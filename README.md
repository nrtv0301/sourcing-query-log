# sourcing-query-log

**人材紹介の「検索式」の当たり外れを、CSVに記録してCIで集計するだけのリポジトリです。**

人を探すとき、LinkedInやGitHubで検索式を組みます。効くものと効かないものがあります。
でもその結果は、たいてい誰の記憶にも残りません。次に同じ職種を探すとき、また同じ空振りをします。

だから、記録することにしました。

```
data/queries.csv  ← 正本。検索式と、その結果を1行ずつ足していく
        ↓  scripts/rank.py（Python標準ライブラリのみ）
docs/queries.md   ← 自動生成。効いた順に並ぶ
        ↓  GitHub Actions
        push するたびに再生成してコミット
```

## 作ってすぐ、思い込みが1つ壊れました

このリポジトリを作る前、私は社内で何度もこう言っていました。

> **「LinkedInの検索は3語まで。4語以上重ねると数件しか出ず死にます」**

18本を集計したら、こうなりました。

| 語数 | 効いた | 空振り |
|---|---|---|
| 1語 | 2 | 2 |
| 2語 | 0 | 1 |
| **3語** | 3 | 1 |
| **4語** | **2** | 1 |

**4語でも2本効いていました。**

効いた4語：`電力 需給 最適化 エンジニア` ／ `テックリード TypeScript React AWS`
空振った4語：`プラント DX 要件定義 エネルギー`（4件しか出なかった）

差は語数ではありませんでした。

- **効いた4語は、実在する職務の並び**です。「電力／需給／最適化／エンジニア」は、そういう仕事をしている人がいます
- **空振った4語は、誰の肩書きでもありません。**「プラント／DX／要件定義／エネルギー」を全部書いている人は、存在しないわけです

3語でも `物流 最適化 エンジニア` は空振っています。**語数ではなく、語が具体的かどうかでした。**

散らばったメモを見ていたときは、これに気づけませんでした。
1箇所に集めて数えたら、5分で分かりました。

## もう1つ、思い込みが壊れました

私は社内でこうも言っていました。

> **「GitHubのユーザー検索は名前とプロフィール文しか読まない。だから `gurobi` では0件になる」**

`location:Japan (gurobi OR pyomo OR ortools OR 数理最適化)` が本当に0件だったので、
そう結論づけていました。**検証はしていませんでした。**

このREADMEを書いているときに「本当にそうか」と聞かれて、初めて調べました。

### 実測1：bioは読まれている

| クエリ | 件数 |
|---|---|
| `AtCoder` | **198** |
| `AtCoder in:login` | 35 |
| `AtCoder in:name` | 7 |
| `AtCoder in:email` | 0 |

**login + name + email を足しても42件。198件には届きません。**
残りはbioにマッチしています。**bioは検索対象に入っています。**

（公式ドキュメントには「`in` を省略した場合、検索されるのは username と email のみ」と
書かれていますが、実挙動と合っていません）

### 実測2：0件だった原因は、まったく別のところにあった

| クエリ | 件数 |
|---|---|
| `gurobi` | **51** |
| `location:Japan gurobi` | **0** |
| `location:Japan AtCoder` | 39 |

**`gurobi` は世界で51人ヒットします。**
0件だったのは `location:Japan` を足したからでした。

そして、その理由も**自分で書いていました。**同じ日のメモにこうあります。

> location は自己申告。**日本のエンジニアの多くは location を書いていない。**
> 書いていない実力者は、この検索では一生ヒットしない。

**原因を書き留めておきながら、結論は「GitHubでは引けない」にしていました。**

「探せない」のではなく、**絞り込みが強すぎただけ**でした。

- 「LinkedInは3語まで」

どちらも**一度うまくいかなかった経験を、法則として一般化していました。**
そして**どちらも検証していませんでした。**

記録を1箇所に集めて数えたら、5分で両方とも崩れました。

## 崩れなかったもの

全部が間違っていたわけではありません。データで裏づけが取れたものもあります。

**学術用語は、肩書きに出ません。**

`オペレーションズリサーチ` はLinkedInで空振りました。
検索には引っかかるのですが、スキル欄にマッチした不動産・クラウド・人事の人が並びます。

一方、`Gurobi` のような**道具の固有名詞**は効きました。
**人は、自分が使っている道具の名前を書くからです。**肩書きには書かなくても。

同じ理由で `構造計画研究所` のような**社名**も空振りました。
社名で引くと、その会社の別部門の人ばかり出てきます。

## 記録のルール

| 列 | 意味 |
|---|---|
| `verdict` | 効いた / 空振り / 未着手 |
| `why` | **なぜそうなったか。ここが空だとCIが落ちます** |
| `found_good` | その検索から、実際に有力候補に至った人数 |

**`why` を必須にしているのが、このリポジトリの肝です。**

「◯◯という検索式は空振りだった」だけの記録は、次に活きません。
**「学術用語は肩書きに出ない」まで書いて初めて、次の検索式が決まります。**

もうひとつ。

> **件数が多いことは、効いたことを意味しません。**
> 94件出ても有力候補が2人なら、それは絞り込みが甘いということです。

だから `result_count`（何件出たか）と `found_good`（何人に至ったか）を別の列にしています。

## 使い方

```bash
python3 scripts/rank.py          # docs/queries.md を生成
python3 scripts/rank.py --check  # 検査だけ（CIで使用）
```

Python標準ライブラリのみ。依存パッケージはありません。

検索を試したら、`data/queries.csv` に1行足して push するだけです。
GitHub Actions が集計して `docs/queries.md` を更新します。

## 誰が作ったか

人材紹介の営業です。エンジニアではありません。

自社のエンジニアが全員退職して0人になったのをきっかけに、
**業務の判断基準をコードとデータで持つ**ことを始めました。これはその一部です。

Pythonが214行、GitHub Actionsのワークフローが51行。
**やっていることは「CSVを読んで、検査して、並べ替えて、Markdownに書き出す」だけです。**

それでも、自分の思い込みより、21行のCSVのほうが正確でした。
